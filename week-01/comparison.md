## 3. What the AI added that I never asked for

- A full web application (Next.js + TypeScript) instead of the "small program" I asked for
- Letter grade bands (A–F) with configurable percentage cutoffs
- Extra statistics not in the spec: median, standard deviation
- A grade-distribution bar chart and a sortable/filterable results table
- CSV export and bulk-paste import features
- A configurable "maximum possible mark" and a pass-threshold slider, instead of a fixed ≥50 rule

## 4. What the AI got wrong or silently skipped

- On the first bulk-paste test (input: `abc`, `xyz`, `50`), Rocket silently dropped the two invalid rows and only showed "1 valid mark entered" — with no indication that 2 rows had been ignored or why. This is exactly the kind of silent failure the lab warns about.
- The Mark input field only accepts numbers, so it's structurally impossible to reproduce case D's raw mixed-text input the same way the manual parser handles it — Rocket sidesteps the hard part of the spec rather than solving it.

## 5. The defect I asked Rocket to fix

**Prompt I used:**
"When I paste marks and some rows are invalid (not a number, or not between 0-100), the import silently ignores them. Please show a message after import telling the user how many rows were skipped and why (e.g. '2 rows skipped: not valid numbers'), so nothing gets silently dropped."

**Result:** Fixed. Rocket added a warning toast ("Imported 1 mark. 2 rows skipped: 2 not valid numbers.") and split skip reasons into categories ("not valid numbers" vs "out of range (0-max)"). It also fixed an unrelated bug on its own — out-of-range values pasted in bulk weren't being caught before, and now they are.

**What this tells me:** Rocket can respond precisely to a well-specified bug report, and it even improved something adjacent I hadn't noticed. But it never caught the silent-drop problem on its own during the original build — I had to find it first by deliberately trying to break the app.

## 6. Reflection (200–300 words)

**1. Which parts of the work did the AI genuinely speed up?**
Rocket built a working, visually polished tool in minutes — something that would have taken me much longer to style and structure by hand, especially the chart and results table. It also did real requirements elicitation: its clarifying questions (who's using this, what threshold) forced me to think about details I might have skipped if I'd just started coding.

**2. Where did the AI cost you time, or give you something that looked right but was not?**
The very first test run gave a wrong pass rate — not because of an AI bug, but because I accidentally moved a slider while exploring the UI. That's itself a lesson: a GUI with hidden state (sliders, defaults) is easier to misconfigure by accident than a script whose logic is fixed in code I wrote myself. The real AI-caused issue was the silently-dropped invalid rows, which I only found by deliberately trying to break it — an unaware user would never have known their data was silently incomplete.

**3. Which of these two artefacts would you be willing to put your name on, and why?**
The manual version. I wrote every line, I know exactly what it does and doesn't handle, and I can defend any part of it in class. I never looked at Rocket's generated source code — I only tested its behavior from the outside, so I can't vouch for its correctness beyond what I happened to test.

**4. What must a human engineer still be responsible for after this experiment?**
Defining the actual rules precisely (what counts as valid, what the pass threshold really is), testing edge cases the tool won't think to try on its own, and reading or reviewing the generated code before trusting it in anything real. AI accelerates production but does not verify itself.
